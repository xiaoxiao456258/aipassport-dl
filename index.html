  1. 先在上面下 v5.3.0_app.bin，存手机里。

  4. 点「选择文件」→ 选 v5.3.0_app.bin → 上传并升级。
  5. 等 1~2 分钟，中途千万别断电。成功后会提示升级成功，设备自动重启。

OTG 线刷整片（设备变砖 / 想恢复新分区表时）

  1. 下 v5.3.0_full.bin（1.64 MB）。
  2. 装烧录 App：ESP32_Flasher（com.esp_flash.esp_flash_app）或 ESPFlash（io.serialflow.espflash）。
  3. 用 C to C 数据线连板子（纯充电线枚举不出来，最常见的坑）。
  4. 芯片选 ESP32-C3，先 Erase 整片擦除，再写 偏移 0x0 = v5.3.0_full.bin，波特率 460800（不稳降 115200）。
  5. 连不上：接上的瞬间按住板上键再上电（GPIO9/BOOT 下载模式）。

有电脑时

  1. pip install esptool
  2. esptool --chip esp32c3 -p COM3 -b 460800 erase_flash
  3. esptool --chip esp32c3 -p COM3 -b 460800 write_flash 0x0 v5.3.0_full.bin
只想升 app、不动分区表：write_flash 0x10000 v5.3.0_app.bin。偏移必须是 0x10000，用 0x20000 会 rst:0x3 起不来；必须 DIO / 80M。

固件 5.3.0 改了什么（本次）—— 不加功能，只还两块「现在不出事、以后必出事」的债

① 共享缓冲：从「注释约定」到「租约」：行情与快讯共用一块 9KB 接收缓冲，靠的是 net.h 里一行注释「两者都由网络任务串行调用」。哪天快讯被挪出网络任务、或加第三个使用者，症状不是编译报错，而是两路往同一块内存写、解析到对方那一半 JSON —— 偶发覆盖率掉、快讯乱码，极难查。现在改成 netBufAcquire("market") / netBufRelease()：借不到就返回空、打一行 [net] 缓冲被 news 占用，market 本轮跳过，调方跳过本轮。代价一个指针，把「玄学」变成「日志里一眼看到」。
② 整池替换只留一个入口：appInstallPool()。网页「恢复默认股票池」原来自己手写 storageSave + memcpy + buildRanks，漏了 onPoolChanged —— 换池后告警冷却 alertAt 不清（新票被旧票冷却压住，该闪不闪）、屏幕不重画、不立刻重抓，得等下一轮 5 秒。现在写盘失败就不换内存池（防止「App 说成功、掉电全丢」），成功才换池、重算三榜、触发回调；恢复默认页也补了写盘失败的报错页。
你能感觉到的差别：几乎没有。唯一可见的是「恢复默认池」之后告警立刻正常、下一轮立刻出数。
体积：app 1,662,960 B（1.59 MB）· full 1,728,496 B（1.65 MB）· Flash 94.7%（余约 88 KB）。

固件 5.2.9 改了什么（上一版）—— 合掉两套 OTA、少白等一轮、把报错留下来

① OTA 两套实现合一（唯一有事故风险的一条）：api.cpp（App 推流）和 portal.cpp（网页表单）各自写了一份 Update.begin/write/end，还各自维护一份 s_otaOk —— 同一个 bin、两条路径、两套收尾判断，「网页刷成功、App 刷失败」就是这么来的。现在写入流水线只剩 ota.cpp 一份，两个入口只负责回 JSON 或 HTML。顺带堵了一个真隐患：原来某一块写失败只打一行日志，收尾照样 Update.end(true)，等于把半截镜像标成有效并切分区；现在中途失败就 abort，宁可这次升级失败，也不让你刷成砖。网页升级成功页还会显示实际写入多少 KB。
② 开机首抓延后 300ms：冷启动实测 t=3744 首抓 DNS 失败 → 隔 7.2 秒拿到 body 不完整 got=4080/5675 → 第三次才成功，开机到出数 14.7 秒。真因是 DHCP 刚拿到 IP 就发请求，热点下发的 DNS 还没装进解析器（唤醒路径不撞：醒来是先作废 DNS 再连）。现在开机首抓等 300ms，抓取间隔本身一点没变。
③ BACKUP DNS 兜底：热点常常只下发一个 DNS（/status 里 dns2=0.0.0.0），那一台一抖整机就解析不了。现在每次拿到 IP 后检查备胎槽，空的补 223.5.5.5 —— 只动备胎，不碰主 DNS、网关和 DHCP 租约；lwIP 只在主 DNS 超时后才问它，主 DNS 正常时行为完全不变。
④ 报错不再沉默：platformio.ini 里 CORE_DEBUG_LEVEL=0 会把全部 log_i/log_e/log_w 编译掉（省约 45KB Flash），代价是现场一个错误都看不见，之前判断「NVS 配置校验失败掉回默认池」「OTA 到底为什么写失败」全靠猜。现在把错误/告警级 + 关键一次性事件（开机横幅、连上 WiFi、配置载入与迁移、存储读写行数、OTA 全程、按键、设置项）改走 DBG_* 进环形缓冲，/api/v1/log 直接可读。高频刷屏的几条（每轮排名、每 30 秒栈水位）仍然编译掉，不占缓冲。
你会看到：/api/v1/log 出现 [cfg] 已载入 rc=…、[store] 载入 80 行、[ota] 开始 web/form / [ota] 结束 ok=1 size=1662464；出问题把这几十行发出来就能定位，不用再接线读串口。
体积：app 1,662,464 B（1.59 MB）· full 1,728,000 B（1.65 MB）· Flash 占用 94.7%（余约 88 KB）。

固件 5.2.3 改了什么（上一版）—— 修浅睡唤醒后 WiFi 假连接

现象：设备进浅睡、按键唤醒后，屏幕亮了、状态栏显示已连 WiFi，但行情一直不动，/api/v1/status 里覆盖率 cov=0、emFail 一路上涨，只能重启恢复。
根因：5.2.2 的设计假设是"浅睡期间 WiFi 连接自然保持、醒来自动续收"。实测不成立 —— 唤醒后驱动仍报 staState=3、断开计数 disc=0（一个假象），实际关联早已被 AP 回收，任何 TCP 建连都 3 秒超时。而保活逻辑只在"驱动报告未连接"时才重连，于是永远不触发。
修法：改成睡前主动断关联、醒后立刻重连。
· 睡前 WiFi.disconnect(false,false) —— 只断 STA 关联，不切 WiFi 模式、不重启驱动（那是历史红线，会掉线 15~25 秒）
· 醒来立即 WiFi.begin() 重关联（约 1~3 秒），不等 15 秒兜底
· 醒来作废 DNS 缓存 —— 睡几小时后运营商解析结果常变，沿旧 IP 直连会一律超时
· 假连接自救：驱动报已连接但连续两轮抓取失败 → 强制重连（60 秒最多一次），兜住其它场景
· 抓取在途禁止休眠 —— 原来抓取时没有置忙标志，可能在 netTask 读 socket 时进入浅睡，射频断电导致本轮抓废
你会看到的变化：每次休眠醒来会断一下再自动重连（约 1~3 秒）；disc 计数每次休眠 +1，那是主动断的，不是故障。夜间续航同时略有改善（睡时射频完全断电）。

固件 4.9.13 改了什么（上一版）—— 「连上一会儿断开一会儿」

根因WiFi.mode() 在 ESP32 上是 stop → start 整个 WiFi 驱动，STA 必然掉线重连。而 AP 开关这段代码里有两个地方无条件调它：开窗时 WiFi.mode(WIFI_AP_STA)、关窗时 WiFi.mode(WIFI_STA)。于是每次开/关窗 = STA 掉一次线，日志里只有一句轻描淡写的「[ap] 已关闭」
第二个触发点「AP 丢了重建」分支：只要 softAPIP() 读到 0 就重跑一遍 WiFi.mode(AP_STA)。STA 刚重连那一刻正是 APIP 还没恢复的时候 → 又踢一次 → 循环

修法 2抓取失败时不再 WiFi.disconnect()。原来 fetchFailStreak>=4 每 60s 主动断一次重连，数据没恢复、WiFi 还反复掉。现在只在 STA 本身没连上且持续 120s 才重连

固件 4.9.12 改了什么
