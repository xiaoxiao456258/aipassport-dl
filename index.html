最简单的刷法：不用电脑、不用数据线

  1. 先在上面下 v4.9.16_app.bin，存手机里。
  2. 手机 WiFi 连设备热点 AIPASS-STOCK，密码 xiaoxiao123。
  3. 浏览器打开 http://192.168.4.1/ota。
  4. 点「选择文件」→ 选 v4.9.16_app.bin → 上传并升级。
  5. 等 1~2 分钟，中途千万别断电。成功后会提示升级成功，设备自动重启。
选文件只能选 v4.9.16_app.bin，不要选 full.bin —— 整片包会把 bootloader 和分区表一起覆盖，网页 OTA 通道只该送 app 镜像。

OTG 线刷整片（设备变砖 / 想恢复新分区表时）

  1. 下 v4.9.16_full.bin（1.61 MB）。
  2. 装烧录 App：ESP32_Flasher（com.esp_flash.esp_flash_app）或 ESPFlash（io.serialflow.espflash）。
  3. 用 C to C 数据线连板子（纯充电线枚举不出来，最常见的坑）。
  4. 芯片选 ESP32-C3，先 Erase 整片擦除，再写 偏移 0x0 = v4.9.16_full.bin，波特率 460800（不稳降 115200）。
  5. 连不上：接上的瞬间按住板上键再上电（GPIO9/BOOT 下载模式）。

有电脑时

  1. pip install esptool
  2. esptool --chip esp32c3 -p COM3 -b 460800 erase_flash
  3. esptool --chip esp32c3 -p COM3 -b 460800 write_flash 0x0 v4.9.16_full.bin
只想升 app、不动分区表：write_flash 0x10000 v4.9.16_app.bin。偏移必须是 0x10000，用 0x20000 会 rst:0x3 起不来；必须 DIO / 80M。

固件 4.9.16 改了什么（本次）—— 把响应压进一个 TCP 窗口

真因（专家定位）ESP32-C3 的 lwIP 接收窗口 TCP_WND = 5760 B，而一次抓 80 只的响应是 6404 B + 头 ~350 B = 6754 B。响应比窗口还大，所以每次都必须跨窗口：服务器发满 5760 就得停下等我们开窗。一旦第一个窗口里丢了段，缺口后面没有足够的段产生 dupACK，快速重传永不触发，只能等服务器自己的 RTO/persist（几十毫秒起、逐次翻倍）。我们的空闲闸 2500 ms 先到 → 拿到半截 JSON。实测三次截断 5418 / 5367 / 5098 全贴在窗口边缘（5760 − 头 ≈ 5460）下方，正是这个机制。
改法 1：请求按 secid 去重池子允许「同代码多行」（分批持仓），但行情完全一样。80 行里实际只有 70 个唯一 secid，重复的 10 个纯属白传。请求只发唯一的，解析仍遍历整池，重复行照样各自拿到同一份行情 —— 功能零变化
改法 2：名称字段常态不取f14 占约 15 B/只。名称池里已经持久化过，没必要每 5 秒重取。改为：任一行名字为空，或距上次全量超过 30 分钟时才带 f14（防改名 / ST）
体积变化6754 B → 约 4.9 KB，小于 5760 B 窗口，一次发完、服务器随即 FIN，不存在“窗口关了在等开窗”的死角
刷完怎么看/api/v1/log 里 [em3] OK 后面的字节数应从 6404B 变成 约 4800~5000B；[emN] 200 但无有效数据 应明显减少。名字若显示不全，等 30 分钟自动补，或断电重启触发首次全量
体积app 1,642,304 B（sha256 9e7e1ec6…e630）· full 1,707,840 B（e2511cbc…4397）· Flash 93.6%

固件 4.9.15 改了什么（上一版）—— 抓取失败时把响应体拍下来

4.9.14 的修复已验收实测回传：disc:0、discR:0、fwMode:3、up:575。日志里 [ap] 关窗（只清 AP 配置，STA 不动） 后面再没有 [wifi] STA 断开。「连上又断开」这个话题到此结案
剩下的真问题不是断网，是抓行情时好时坏：日志里成片出现 [emN] 200 但无有效数据 5418B / 5098B / 5367B，成功时是 OK 6404B。HTTP 是 200、字节也收到了，但一只股票都解析不出来
为什么以前查不动光有「5418B」这一个数字，三种完全不同的原因分辨不出来：① body 被截断（读一半卡住）② 拿到的是风控页/劫持页 ③ 是完整 JSON 但里面没有数据。三种的修法互斥，猜错就是又白改一版
这版加的东西解析失败时把响应体头 80 字节 + 尾 40 字节打进日志（不可打印字符换成 .），并标出首字节。看一眼就能定性
判据头是 { 且尾是 } → 完整 JSON，问题在口径/停牌
头是 { 但尾不是 → 半截 JSON，链路或射频把连接掐了
头不是 {（常见 <） → 风控页 / 运营商劫持
怎么用刷完等两三轮抓取，照旧发 /api/v1/log。新增日志形如 [em1] 头[7B] {"rc":0,... 与 [em1] 尾 ...}

固件 4.9.14 改了什么（上一版）—— 「连上一会儿断开一会儿」真因

上一版为什么没修好4.9.13 关窗改成了 WiFi.softAPdisconnect(true)，注释写「只关 AP、不动 STA」。参数 true 恰恰就是"把整个 WiFi 关掉再重开"，动作跟被删掉的 WiFi.mode(WIFI_STA) 完全一样
源码链路softAPdisconnect(true) → WiFi.enableAP(false)（WiFiAP.cpp:231）→ mode(APSTA & ~AP) = WIFI_STA（WiFiGeneric.cpp:1348）→ esp_wifi_set_mode()。IDF 在 WiFi 已启动时调 set_mode 会内部 stop → set → start，整个驱动重启
所以现象是这样来的AP 窗口默认 2 分钟，到期关窗 → 驱动重启 → STA 掉线 → 15~25s 重连 → 恢复 → 再开窗/再到期 → 再掉。每 2 分钟自踢一次，完全是代码自己干的
同款雷还埋在两个地方WiFi.disconnect(true, false) 的 true → enableSTA(false) → mode(AP)：不但重启驱动，还把 STA 从模式里摘掉，要等下一次 begin() 才补回来 —— 中间那段"怎么都连不上"就是它。改配置、强制重连两处都有
修法 1：模式只定一次开机 WiFi.mode(WIFI_AP_STA) 固定下来，运行期全程序不再调 WiFi.mode()。开窗 WiFi.softAP() 只改 AP 配置；关窗 softAPdisconnect(false) 只清 AP 配置（wifioff=false 不碰驱动）
修法 2：disconnect 全部改 false改 WiFi 配置、长时间连不上强制重连，都只断 STA 关联，不动模式、不动 AP 接口
修法 3：有客户端不许关窗关窗前判 softAPgetStationNum()，手机连着就不关（除非等满 2 分钟强关）。原来主循环直接关，绕过等待队列，正在传的数据全丢
新增 up / rr / fwMode以前分不清"WiFi 掉线"和"设备重启"——手机上看一模一样。现在 /status：up=开机秒数，rr=复位原因（1 上电 3 软件 4 panic 5 中断看门狗 6 任务看门狗 8 深睡 9 棕断），fwMode=当前 WiFi 模式（应为 3 = APSTA）。up 很小而设备开了很久 = 重启，不是掉线
日志能看见窗口了power.cpp 的开窗/关窗原来用 log_i，生产版全被编掉。现在改 DBG_*，/api/v1/log 能直接看到 [power] AP 窗口开启/关闭 与 [ap] 关窗（只清 AP 配置，STA 不动）
怎么验收/status 里 disc 不再随时间猛涨、fwMode:3 恒定；/log 里若出现 [ap] 关窗，紧跟其后不应再出现 [wifi] STA 断开

固件 4.9.13 改了什么（上一版）—— 「连上一会儿断开一会儿」

根因WiFi.mode() 在 ESP32 上是 stop → start 整个 WiFi 驱动，STA 必然掉线重连。而 AP 开关这段代码里有两个地方无条件调它：开窗时 WiFi.mode(WIFI_AP_STA)、关窗时 WiFi.mode(WIFI_STA)。于是每次开/关窗 = STA 掉一次线，日志里只有一句轻描淡写的「[ap] 已关闭」
第二个触发点「AP 丢了重建」分支：只要 softAPIP() 读到 0 就重跑一遍 WiFi.mode(AP_STA)。STA 刚重连那一刻正是 APIP 还没恢复的时候 → 又踢一次 → 循环
修法 1WiFi.getMode() != WIFI_AP_STA 才切 mode；关窗只做 softAPdisconnect(true)，不动 STA
修法 2抓取失败时不再 WiFi.disconnect()。原来 fetchFailStreak>=4 每 60s 主动断一次重连，数据没恢复、WiFi 还反复掉。现在只在 STA 本身没连上且持续 120s 才重连
修法 3打开 WiFi.setAutoReconnect(true)，掉线由驱动自己恢复，不靠上层踢
新增 disc / discR注册 WiFi 事件回调，记录上电以来断开次数与最近一次原因码：15=四次握手超时 · 8=对端（手机热点）踢开 · 200=收不到 beacon · 3=认证超时 · 205=连接失败。/status 直接看，日志有 [wifi] STA 断开 reason=n

固件 4.9.12 改了什么

对比结论v1.7.7 每请求新建 socket + Connection: close + 读循环 10s；4.9.x 复用静态 socket（keep-alive）+ 零字节 900ms 砍 + 头闸 3s + 每口只 3.5~7s。慢链路上这些"优化"全在砍正在到的数据
真 bug 1：setTimeout 单位WiFiClient::setTimeout(seconds) 形参是秒。旧代码传 NET_CONNECT_MS=2000，内部变成 2,000,000ms → 连接闸形同虚设，实测一次 connect 卡 18211ms，整轮预算一把烧光（日志那句「整轮预算用尽」就是它）。改用 connect(ip, port, timeout_ms)
真 bug 2：死连接判不出来connected() 用 recv(...,MSG_DONTWAIT) 判活，对端发 FIN 时返回 0 且 errno 为空 → 仍返回 true。keep-alive 复用的死 socket 发现不了，第一次尝试必然写进死连接。现在每次 stop() 后新建
真 bug 3：请求可能没发完write() 是 select(20ms)+有限重试，可能只写一部分并静默返回。现在核对写入字节数，短写直接判失败（日志 w= 就是它）
闸门重定连接 3s（真闸）· 读头 8s · body 空闲 2.5s · 首口 14s / 后续口 12s · 整轮 55s
熔断放宽3 连败→15s 改成 5 连败→30s。原来等于把四个口轮流打成 OPEN，只剩半开单发探测 —— "偶尔通一下"就是它
自愈降频连败复位 20s→60s，看门狗 4→6 个间隔。原来每 15s 清一次 DNS 与熔断，退避永远长不起来
停用 beacon 拉长定量核算：beacon 占空比 1.75%、客户端轮询 0.25%，合计约 2%；6.7KB 响应只需 ~12ms 空口。富余两个数量级 → 4.9.11 的方向不成立，且 600 TU 有让手机掉 AP 的风险
日志新增三个数[em1] … w=1005 n=0 f=-1：w=请求写出的字节 · n=收到的字节 · f=首字节时刻。零回包时靠这三个数区分「请求没发完」和「发完了对端不回」，不用再猜
status 加 psReal读驱动里真正生效的省电档（esp_wifi_get_ps）。原来的 ps 只是自己记的变量，不能证明驱动接受了

固件 4.9.11 改了什么

4.9.10 的实测结果同一轮里换了 5 个不同 CDN IP（61.129.129.196 / 47.112.165.11 / 43.144.251.121 / 117.184.40.129 / 115.231.230.218），TCP 全部 33~147ms 通，读响应头全部卡满 2.3~3s、零字节。换 IP 完全无效，IP 假设排除
真正的规律回头翻日志：4.9.9 那次唯一成功 [em1] OK 6450B 392ms 发生在 t=3238 —— AP 还没开窗、没有任何 AP 客户端的时刻。一旦手机连上热点看页面（apClients:1），抓取必定零回包
机理C3 单射频 APSTA 同信道靠分时：AP 每 102.4ms 必须发 beacon 并服务已连客户端，浏览器还在每 2s 轮询 /api/v1/status。STA 的连续 RX 窗口被切碎 —— 握手包能过（我们主动发 SYN，射频正对着 STA），几百字节的 HTTP 响应凑不齐
改动抓取窗口内把 AP beacon 间隔 100 → 600 TU（6 倍），抓完立刻恢复。客户端不掉线，射频占用大幅下降。[net] 抓取开始 apClients=… ps=… 写日志
status 加 apCh实际射频信道。ch（STA 信道）与 apCh 不相等 = APSTA 跨信道，收包必碎，是另一种故障

固件 4.9.10 改了什么

定案证据4.9.9 的 /api/v1/portal 里，东财 58.221.54.26 回了 HTTP/1.1 418、首字节 110ms、写入 151B —— HTTP 回包是真能收到的。同一次启动日志里 [em1] OK 6450B 392ms、fetch-bg OK src=1，行情直接就有了
真凶push2.eastmoney.com 是 CDN，每次解析给的 IP 不同：117.184.40.129 → 43.144.251.121 → 58.221.54.26。其中有的 IP 的 80 口在听（TCP 78ms 通）、但 HTTP 层被墙（零回包）。而 DNS 缓存没有 TTL、永不重解 —— v4.9.4 删掉「每轮 netReset」之后，再没人清缓存。首次撞上黑洞 IP，就永久绑死在它上面：DNS 12ms、TCP 通、永远 0 字节
修法 1：缓存加 TTLDNS 缓存 5 分钟过期，过期强制重新解析（DNS_TTL_MS）
修法 2：失败即丢该域名同一 host 连败 2 次 → dnsForget() 丢掉缓存条目，下次真的去问 DNS 换 IP。只在失败时丢，不会退化成 4.9.4 那种每轮清空
修法 3：同一次抓取内就换 IP第一次零回包立刻 dnsForget + 第二次 attempt 前重解析，拿到新 IP 再连 —— 原来第二次只是「同 IP + HTTP/1.0」，CDN 给黑洞 IP 时换协议救不了

固件 4.9.9 改了什么

尾斜杠别名WebServer 的 URI 是精确匹配，/api/v1/portal/ 不会命中 /api/v1/portal。手输地址多一个斜杠就 404 —— status / scan / diag / portal 四个只读口全部补上别名
404 日志现网可见原来用的是 log_w，被 CORE_DEBUG_LEVEL=0 编掉了，现网 404 一个字节都看不到。改 DBG_W 写 logBuf，打完错路径后 /api/v1/log 能直接看到 [api] 404 GET /xxx
portal 探测留痕开始与结论都写日志（[portal] 开始探测 gw=… / [portal] verdict=…），接口到底有没有被调用一目了然

固件 4.9.8 改了什么

结论先行4.9.7 的 ps=2 已证明设备抓取时 WIFI_PS_NONE 生效，回包依然是 0 字节 —— 设备省电不是真凶。DNS（12ms）、TCP 握手（62~102ms）都通，只有 HTTP 载荷回不来，只剩「链路上被截走」这一种解释
